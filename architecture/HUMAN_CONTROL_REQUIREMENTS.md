人类控制需求文档

文档定位: 定义人类对 Agent 编排的控制能力，明确已实现项与待实现项的需求边界。
人类控制为最高优先级，任何编排行为都应能被人类控制指令中断或覆盖。
本文档是需求契约，不含实现代码。不依赖具体渠道，通过通用 Mention 与 Reply 模型表达。

一、核心原则

1. 人类控制具有最高优先级，优先于任何自动编排决策。
2. 人类控制指令一旦发出，进行中的编排应能被中断、暂停或改派。
3. 人类控制不依赖具体渠道，通过通用 Mention 与 Reply 模型表达，
   不绑定 Telegram 的 @、reply_to_message_id 等专属字段。
4. 人类控制既可来自通道消息（@、回复），也可来自 Control Plane 本地 API。
5. Bot 发起的消息不构成人类控制，防环。

二、已实现的能力

1. 直接 @: 人类显式 @某 Agent，仅该 Agent 响应，其余 Agent 静默。
   这是当前最基础的人类指定执行者的方式。
2. Reply 指定: 人类回复某 Agent 的消息，仅被回复的 Agent 响应，
   被回复消息文本作为参考上下文。
3. @Hermes 请求编排: 人类 @编排 Agent，由编排 Agent 决定委派给哪些 Worker，
   可单 Agent 委派、并行编排或顺序编排。
4. 多 @: 人类一条消息 @ 多个 Agent，仅被 @ 的 Agent 响应。
5. 普通消息静默: 群聊普通消息不触发任何 Agent，保证人类不被误打扰。

三、待实现的能力（只定义需求，不实现）

1. 插话
   需求: 人类在编排进行中插入新指令，编排应识别插话并据此调整当前或下一步。
   边界: 插话不强制终止当前进行中的子任务，但影响后续步骤。
   状态: 待实现，本阶段只定义需求。

2. 暂停
   需求: 人类可暂停某个编排或某个 Agent，暂停期间不接收新编排委派。
   边界: 暂停是可恢复的，暂停状态可被查询，已暂停的 Agent 不被路由选中。
   状态: 待实现，本阶段只定义需求。

3. 取消
   需求: 人类可取消某个进行中的编排或子任务，已取消的不继续执行。
   边界: 取消是即时的，取消后编排结果不回写，取消状态可被查询。
   状态: 待实现，本阶段只定义需求。

4. 改派
   需求: 人类可把某任务从一个 Agent 改派给另一个 Agent，原 Agent 不再处理。
   边界: 改派携带原上下文，改派后由新 Agent 接续，改派记录可追溯。
   状态: 待实现，本阶段只定义需求。

四、控制指令的通用表达

1. 控制指令通过通用 Mention 与 Reply 模型表达，不使用通道专属字段。
2. 来自通道的控制指令由 ChannelAdapter 映射为通用 Mention 与 Reply，
   再由 Control Plane 解释为控制语义。
3. 来自 Control Plane 本地 API 的控制指令直接表达控制语义，
   不经过通道层。
4. 控制语义与通道无关，同一控制指令在 Telegram、飞书、Web 上行为一致。

五、优先级与冲突处理

1. 人类控制指令优先于自动编排决策。
2. 同时收到多个人类控制指令时，按时间顺序处理，后到的可覆盖先到的。
3. 取消指令优先于暂停，暂停中的编排也可被取消。
4. 插话不覆盖已发出的取消或改派。

六、状态对照（控制指令的结果状态）

1. 操作成功: 控制指令生效，返回当前编排状态。
2. 操作失败: 目标编排不存在、目标 Agent 离线、指令格式错误，分别提示。
3. 输入异常: 空指令、未知控制类型、缺目标 Agent，分别提示。
4. 状态差异: 目标已暂停时再暂停、目标已取消时再取消，提示当前状态。
5. 频率限制: 短时间内重复控制指令应合并或拦截，防止抖动。

七、不做的事

1. 不在本阶段实现插话、暂停、取消、改派的运行时代码。
2. 不绑定任何具体渠道的控制语法。
3. 不把人类控制能力与某个 Agent 的内部实现耦合。

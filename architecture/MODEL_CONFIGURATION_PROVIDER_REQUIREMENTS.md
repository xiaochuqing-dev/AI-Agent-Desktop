模型配置管理边界需求文档

文档定位: 定义各工具模型配置的管理权归属，避免多方同时写同一份配置导致冲突。
本文档是需求契约，不含实现代码。真实 API Key、OAuth Token 一律使用占位符，
如 <MODEL_API_KEY>、<OAUTH_TOKEN>。

一、核心原则

1. 每个工具的模型配置只能有一个管理权归属，由归属方写入，其余方只读。
2. 管理权归属分四类: 本应用原生管理、官方登录管理、CC Switch 管理、外部管理。
3. 本应用与 CC Switch 不得同时写同一份配置。
4. 新手首次安装时，模型配置不得以 CC Switch 为强制依赖。

二、Hermes 基础模型配置

1. Hermes 的基础模型配置必须由本应用原生支持。
2. 本应用负责 Hermes 的模型选择、基础参数、启用开关等配置的写入与读取。
3. 该配置的管理权归属本应用，CC Switch 与外部管理不介入。
4. 真实凭据（如 <MODEL_API_KEY>）由凭据管理统一保管，配置只引用占位符。

三、Claude Code 与 Codex

1. 支持官方登录引导: 本应用引导用户走 Claude Code、Codex 的官方登录流程，
   不替用户代填官方凭据。
2. 支持状态检测: 本应用可检测官方登录是否完成、是否有效，并反馈状态。
3. 支持基础 API 配置: 本应用可写入基础 API 配置项（如 endpoint、超时），
   不覆盖官方登录产生的凭据。
4. 管理权归属: 走官方登录的工具，登录态归官方登录管理；
   走基础 API 配置的工具，配置归本应用管理。二者不混写同一份。

四、CC Switch

1. CC Switch 只作为可选的高级模型供应商管理入口。
2. CC Switch 不得成为新手首次安装的强制依赖。首次安装时不要求安装或配置 CC Switch。
3. 用户主动选择使用 CC Switch 时，由 CC Switch 管理其负责的模型供应商配置。
4. CC Switch 管理的配置，本应用只读不写，避免双方同时写同一份配置。
5. CC Switch 与本应用的配置管理范围应明确划分，互不重叠。

五、管理权归属规则

1. 每个工具进入管理前，先判定管理权归属，归属方唯一。
2. 归属判定后，非归属方对该配置只读。
3. 归属判定可由用户显式切换，切换时先完成配置移交再切换归属，不并发写。
4. 归属状态可查询，本应用可显示每个工具当前由谁管理。
5. 四类归属互斥: 一个工具同一时刻只能归一类。

六、配置写入的冲突防护

1. 本应用写入前检查目标配置的归属，非本应用归属则不写，提示用户。
2. 本应用与 CC Switch 通过归属标记或文件锁避免并发写同一份配置。
3. 官方登录产生的凭据文件，本应用与 CC Switch 均不覆盖写入。
4. 任何写入操作前备份当前配置，写入失败可回滚。

七、状态对照（配置管理的操作结果）

1. 操作成功: 配置写入生效，归属标记更新。
2. 操作失败: 归属不匹配、配置文件不可写、凭据无效，分别提示。
3. 输入异常: 配置项缺失、格式错误、超出允许范围，分别提示。
4. 状态差异: 已由官方登录管理的工具被本应用尝试写入，提示归属冲突。
5. 频率限制: 短时间内重复切换归属或重复写入应拦截，防止抖动。

八、不做的事

1. 不替用户代填 Claude Code、Codex 的官方登录凭据。
2. 不把 CC Switch 设为首次安装强制依赖。
3. 不与 CC Switch 同时写同一份配置。
4. 不在配置文件中写入真实 API Key、OAuth Token，只引用占位符。

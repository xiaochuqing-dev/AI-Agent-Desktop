组件长期定位 COMPONENT_POSITIONING

本文档逐个说明本产品涉及组件的长期角色、是否长期保留、可替换性、以及何时可以删除。
所有判断以产品宪法和当前运行事实为准，不因临时实现细节改变长期定位。

--------------------------------

Hermes

角色：默认智能中枢和 Orchestration Provider，群聊治理、委派、共享内存的核心。
是否长期：是，当前默认核心。
可替换性：架构上作为 Provider 存在，将来可被更强的同类中枢替换；但替换属于重大架构变更，不是常规操作。
何时可删：不删。除非产品方向整体放弃中枢委派模式，否则 Hermes 是默认中枢。

--------------------------------

Claude Code

角色：一等代码 Agent，由 cc-connect 接入 Telegram，承担群内代码类任务。
是否长期：是，一等 Agent。
可替换性：作为 Agent Provider 存在，可增减同类代码 Agent，不影响中枢与渠道层。
何时可删：用户主动停用该 Agent 时，从配置中移除即可，不影响其余链路。

--------------------------------

Codex

角色：一等代码 Agent，由 cc-connect 接入 Telegram，与 Claude Code 并列。
是否长期：是，一等 Agent。
可替换性：同 Claude Code，作为 Agent Provider，可独立增减。
何时可删：用户主动停用时移除，不连带影响 Claude Code 或 Hermes。

--------------------------------

cc-connect

角色：当前辅助 Runtime 和 Telegram 连接层，把 Claude Code、Codex 接入 Telegram，并把消息事件回传给 Hermes。
是否长期：当前保留，但不是永久核心，明确标记为可替换。
可替换性：架构上作为 Adapter 存在，将来上游能力补齐或出现更好方案时可整体替换。
何时可删：当其承担的连接与回传职责可由更原生的方案覆盖，且三条链路迁移完毕后，可整体移除。

--------------------------------

Telegram

角色：首发 Channel，当前唯一在用的消息渠道。
是否长期：渠道本身长期保留，但"唯一渠道"的地位不长期。
可替换性：渠道层必须可扩展，飞书等渠道将来作为同级 Channel 接入，不改动中枢与 Agent 层。
何时可删：不删渠道能力。单个渠道实例在用户停用时移除即可。

--------------------------------

飞书等未来渠道

角色：规划中的同级 Channel，与 Telegram 同处渠道层。
是否长期：当前不在本阶段范围，但架构为其预留位置。
可替换性：与 Telegram 同构，作为 Channel Adapter 接入。
何时可删：未实现，不存在删除问题；实现后按单个渠道实例处理。

--------------------------------

dual_agent

角色：当前 Fallback 编排层，负责并行与顺序编排，以 junction 形式存在。
是否长期：不是永久核心，明确标记为临时能力。
可替换性：当 Hermes 原生支持同等编排能力后，其职责回归 Hermes，dual_agent 退场。
何时可删：当 Hermes 原生支持 parallel 和 sequential 编排，且三条链路验证无回归后，可整体移除 dual_agent 包与对应 junction。

--------------------------------

cc-connect Patch

角色：当前兼容层，补齐上游 cc-connect 缺失的路由、Hook 透传、消息回传等能力。
是否长期：不是永久核心，明确标记为临时补丁。
可替换性：每个 Patch 对应一个上游缺陷，上游修复后对应 Patch 失效但无害。
何时可删：按 Patch 逐个评估。上游对应能力修复并经本应用验证后，移除该 Patch。
整体移除时机：五个 Patch 全部被上游覆盖，且 cc-connect 升级后三条链路无回归时，可清空整个 Patch 集。

--------------------------------

总原则

长期组件是中枢、Agent、渠道三层。中间的 cc-connect、dual_agent、Patch 都是"当前不得不有"的临时层。
任何临时层的扩大都需经产品宪法第七条审查。临时层的退场条件必须可验证，不可无限期保留。
